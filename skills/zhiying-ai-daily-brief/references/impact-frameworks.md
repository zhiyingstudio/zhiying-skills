# 影响分析的四种框架

写"影响"这一句时，用以下框架之一切入，避免写出空话。

---

## 框架一：成本结构视角

**问**：这件事改变了谁的什么成本？

| 成本类型 | 追问 |
|---|---|
| 算力成本 | 单位推理成本上升还是下降？幅度？ |
| 人力成本 | 哪个环节的工时被压缩？压缩多少？ |
| 迁移成本 | 换方案要重做什么？数据、代码、流程？ |
| 合规成本 | 新增什么申报、备案、审计义务？ |

**示例**：
> 上下文窗口从 12.8 万提升到 200 万 token，长文档产品无需再做分段摘要工程，单文档处理链路的代码量可减少约一半；但单次调用成本上升，高频场景需重新测算盈亏线。

---

## 框架二：能力边界视角

**问**：这件事把"做不到"变成了"做得到"吗？

分三档描述：

| 档位 | 表述 | 说明 |
|---|---|---|
| 从不能到能 | 此前无法完成，现可完成 | 最强信号 |
| 从能到好用 | 可实现但成本/质量不可接受，现可接受 | 中等信号 |
| 从好用到更好 | 边际改进 | 弱信号 |

**示例**：
> 此前需要 3 小时人工整理的会议录音，现在可 10 分钟内产出初稿，但人名与专业术语仍需人工校对——属于「从不能到能」但质量下限不稳。

---

## 框架三：竞争格局视角

**问**：谁的位置变了？

| 角色 | 追问 |
|---|---|
| 头部 | 优势被巩固还是被削弱？ |
| 中小 | 有无新的切入缝隙？ |
| 上下游 | 议价权往哪边移？ |
| 替代方案 | 是否被直接替代？ |

**示例**：
> 开源同等能力模型后，做同类闭源 API 转售的中间商失去价格优势；而具备行业数据与交付能力的集成商不受影响，反而多了一个低成本底座。

---

## 框架四：时间窗视角

**问**：影响什么时候显现？

| 时间窗 | 典型事件 |
|---|---|
| 立即（周内） | 定价调整、API 下线、漏洞披露 |
| 短期（1–3 月） | 产品迭代、开发者迁移 |
| 中期（3–12 月） | 融资落地、监管过渡期结束 |
| 长期（1 年以上） | 技术路线更替、人才结构变化 |

**此处必须谨慎** —— 时间窗越长，推测成分越大。**超过 3 个月的判断必须标注「推测」。**

## 反模式清单

| 反模式 | 问题 | 修正 |
|---|---|---|
| 「行业将重新洗牌」 | 无主体、无机制、无时间 | 指出具体哪类公司因何原因受影响 |
| 「利好全产业链」 | 无法证伪 | 指出具体环节与传导路径 |
| 「这标志着XX时代到来」 | 宏大叙事，无信息量 | 删除 |
| 「某某慌了」 | 拟人化臆测 | 改为客观格局描述 |
| 「普通人该怎么办」 | 越界建议 | 删除，或改为"哪类岗位的工作内容会变化" |
| 「预计明年将达到XX亿」 | 无来源的预测数字 | 引用来源并标注为机构预测 |

---

## 组合使用

一条信息的影响通常需要两个框架：

**低成本模板**（大多数条目用这个）：

```
成本结构（谁的成本变了） + 时间窗（多久显现）
```

**重点条目模板**：

```
能力边界（从X到Y） + 竞争格局（谁得利谁受损） + 时间窗（含推测标注）
```

## 自检

写完"影响"这一句，自问：

- [ ] 能否被证伪？不能 → 是废话，重写
- [ ] 有没有具体主语？"行业""市场""大家"都不是主语
- [ ] 有没有超出事实的因果推断？有 → 标注「推测」
- [ ] 换成另一条同类新闻，这句话还成立吗？成立 → 说明没写出本条的特殊性
