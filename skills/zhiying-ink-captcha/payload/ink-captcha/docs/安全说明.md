# 安全说明

本文档说明 ink-captcha 的安全边界、威胁模型，以及**明确不防**的攻击。

阅读本文前请先明确一件事：

> **ink-captcha 不是「不可破解」的。它的目标是把批量脚本的成本抬到高于收益。**

如果你面对的是针对性攻击（有人专门盯着你的站点写脚本），验证码只是防线之一，
必须叠加风控策略。详见[第 5 节](#5-明确不防的攻击)。

---

## 1. 威胁模型

我们假设攻击者能够：

- 完整抓包，看到所有 HTTP 请求与响应
- 读取前端 JS 全部源码
- 反复调用你的接口（在限流允许的范围内）
- 编写自动化脚本模拟浏览器行为

我们**不假设**攻击者能够：

- 获取你的 `CAPTCHA_SECRET`
- 在你的服务器上执行代码
- 中间人篡改 HTTPS 流量

## 2. 防护层次

### 第一层：答案加密（AES-256-GCM）

正确点击顺序（元素 id 序列）被加密成 token 下发：

```js
// 下发的 token 长这样
"M0Z-KXy2pQ_9aNf.v3Hs2Kd8LmQ4wZ1xP.yT6bN8cR7eV2mU4h"

// 解密后的内容（攻击者看不到）
{ "order": ["kR3fA","9mXqL","Zt7vB","pQ2wN"], "challengeId": "...", "ts": 1758604800000 }
```

密钥派生：

```js
const KEY = sha256("ink-captcha:" + SECRET);   // 32 字节
```

**安全性取决于 SECRET 的强度**。SECRET 泄漏 = 攻击者可任意伪造 token，
验证完全失效。请当作数据库密码来管理。

> 为什么用 `sha256(前缀 + secret)` 而不是直接用 secret？
> 一是把任意长度的 secret 归一到 32 字节（AES-256 要求），
> 二是加前缀做域隔离（同一个 secret 在别的模块派生出的密钥不会撞车）。

### 第二层：一次性凭证

```js
function consumePassToken(passToken) {
  const ts = passTokens.get(passToken);
  if (ts === undefined) return false;
  passTokens.delete(passToken);        // ⬅ 先删，再判时效
  if (Date.now() - ts > passMaxAgeMs) return false;
  return true;
}
```

**先删后判**，而不是「先判后删」。这样即使有时效判断，凭证也不会在并发请求下被用两次。

凭证本身是 `crypto.randomBytes(18)` → 144 bit 熵，暴力猜测不可行。

### 第三层：尝试次数上限

```
单挑战最多 5 次尝试，超限删除该 challengeId 的计数并作废
```

**这个限制的实际强度**：8 个字里选 4 个并按顺序排列，有序组合数

```
P(8,4) = 8 × 7 × 6 × 5 = 1680
```

5 次机会命中概率 = 5/1680 ≈ **0.30%**。

但注意：攻击者可以**不断申请新挑战**（每次又是 5 次机会）。
所以第三层必须和第四层（IP 限流）配合才有意义。

### 第四层：IP 限流

```
签发：60 次 / 分钟 / IP
校验：20 次 / 分钟 / IP
```

假设攻击者能拿到 100 个代理 IP，那么每分钟最多尝试
`100 × 20 = 2000` 次。要从 1680 种组合中命中，期望需要 1680/2000 ≈ **0.84 分钟**
就能撞对一次。

**所以单靠限流也不够 —— 真正让它不划算的是「每次尝试都需要一次人工/模型识别」**：
攻击者拿到挑战后，必须先"看懂"画面上的 8 个字分别是什么、位置在哪，
才能构造正确的点击序列。这一步无法纯代码完成（除非重训 OCR 模型，
而我们的旋转 + 白描边 + 山形叠加正是为了提高 OCR 难度）。

### 第五层（辅助）：时序特征

```js
// 全部相邻点击间隔 < 60ms → too_fast
```

真人连点 4 个目标，总耗时必然 > 150ms（含视觉搜索 + 鼠标移动）。
脚本常一次性提交全部 id（间隔 0）。

**这只是一道辅助判据**，设计上刻意宽松（只在**全部**间隔都 <60ms 时触发），
避免误伤手速快的用户。单独靠它挡不住有耐心的脚本作者
（在点击之间 `sleep(100)` 即可绕过），但能刷掉低质量的一次性脚本。

## 3. 为什么「答案在响应体里」不算漏洞

这是最常被质疑的点，单独说明。

### 质疑

> 你返回的 `chars` 数组里有所有字和坐标，脚本直接找出 4 个目标字的位置不就过了？

### 回应

**底图上的字必须让用户看见，否则人类无法作答。** 这是可用性的硬约束。

这与「把答案藏起来」存在本质冲突 —— 除非：

- 用 WebP/图片把字画进图里（那脚本照样能用 OCR 识别，只是成本略高）
- 前端用 canvas 自己画字（字面数据仍要下发，只是换了个位置）

**真正的防护不是「藏字」，而是前面那五层**。
即使脚本完美识别了所有字和位置，它仍然要：

1. 走完整流程（先 GET 挑战，不能跳过）
2. 在 5 分钟时效内提交
3. 不超过单挑战 5 次尝试
4. 不超过 IP 限流
5. 点击间隔看起来像人

而这其中的瓶颈是**第 5 点隐含的成本**：识别画面上的 8 个字需要 OCR/多模态模型，
每次调用都是真金白银。当「过一次验证码的成本 > 你的业务价值」时，
攻击者自然放弃了 —— 这才是我们追求的目标。

> **反过来说**：如果你为了「藏字」把可读性搞差（比如字的对比度太低、
> 旋转角度过大），结果是**真人过不去，脚本用打码平台照样过**。
> 这是最差的结局，我们刻意避开了它。

## 4. 已实现的加固细节

### 字段剥离

服务端内部的 `_isTarget` 标记在下发前被显式剥掉：

```js
chars: chars.map(({ id, char, x, y, rotate, size }) => ({ id, char, x, y, rotate, size })),
```

自测里有对应断言，检查 `JSON.stringify(challenge)` 后连字符串 `"isTarget"` 都不出现：

```js
t("chars 里不含 isTarget / _isTarget 字段（关键：不能泄漏）", () => {
  const ch = captcha.createChallenge();
  const raw = JSON.stringify(ch);
  assert.ok(!raw.includes("isTarget"), "响应体里出现了 isTarget 字样");
});
```

> 即使不小心泄漏了 `isTarget`，攻击者也仍需知道「目标的点击顺序」——
> 而顺序信息只存在于加密 token 中。所以这项加固是**纵深防御**，不是单点依赖。

### 定长比较

```js
if (a.length !== b.length || !crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b)))
```

用 `timingSafeEqual` 逐项比对，避免通过响应时间推断密文内容。

### 目标字位置分散化

这一项既是安全考量也是体验考量。

仅靠 shuffle「字 ↔ 位置」的对应关系是不够的 —— 它只保证目标字不固定占前排，
但实测会出现「4 个目标字全挤左半区」的情况。这会让脚本的搜索空间显著变小
（不必扫描全图，只看左侧就行）。

所以额外做了一轮**爬山法**，最大化目标字两两之间的最小距离：

```js
// 反复做「目标位 ↔ 干扰位」交换，直到最小两两距离无法再拉大
while (improved && guard < 60) { ... }
```

自测量化了这个指标（200 次抽样的中位数与第 10 百分位）：

```js
t("目标字彼此分散（最小两两距离中位数 ≥ 70px）", () => { ... });
```

### 布点用 CSPRNG

抽题、布点、洗牌、id 生成全部用 `crypto.randomInt` / `crypto.randomBytes`，
**不用 `Math.random`**。

> `Math.random` 只有两个合法用途：底图的视觉随机（山形起伏、噪点位置），
> 以及默认的 seed 生成。这些都与安全答案无关。

### 印章避让

底图右下角有一枚装饰性朱红印章。布点时会显式排除该区域，
防止字与印章视觉打架 —— 这不只是美观问题：**字压在印章上会降低可读性**，
而可读性下降会伤害真人（脚本反而不受影响）。

## 5. 明确不防的攻击

诚实地列出边界，比假装全能更有用。

### ❌ 打码平台

专业人员/模型可以准确识别并点击。这是所有图形验证码的共性，
reCAPTCHA / 某验 / 某盾同样防不住。
**应对**：把验证码成本转嫁给攻击者（我们已做到），并叠加业务风控。

### ❌ 真人众包

找一群人手动过验证码（俗称「打码农场」）。
**应对**：无技术手段，只能靠业务风控（同一设备/IP 短时间大量注册）。

### ❌ 分布式低频攻击

1000 个 IP，每个只尝试 1 次 → 完全绕过 IP 限流。
**应对**：设备指纹、账号关联分析、注册速度异常告警。

### ❌ SECRET 泄漏后的任意伪造

攻击者拿到 secret 可以离线构造任意合法 token。
**应对**：密钥管理、定期轮换（注意轮换会让在途挑战全部失效）。

### ❌ 中间人攻击

未上 HTTPS 时 token 可被截获重放。
**应对**：上 HTTPS。这是必须项，没有妥协空间。

### ❌ 无障碍对抗

视觉障碍用户无法完成点选。
**应对**：提供替代通道（语音验证码 / 短信验证）。这不是安全漏洞，
但**是必须处理的产品缺陷** —— 否则你等于把一部分真实用户永久挡在门外。

## 6. 加固建议（按性价比排序）

如果你要进一步收紧：

1. **把验证码失败次数写入账号维度**，而不只是 IP。同一账号连续失败 20 次
   直接要求短信二次验证。
2. **前置轻量校验**（见[接入指南第 5 节](./接入指南.md#5-处理验证通过后表单被提交但业务失败)），
   减少无效的凭证消费，间接降低爆破速率。
3. **挑战签名加时间戳 + 服务器侧 nonce 表**，防止同一挑战被多次使用
   （当前实现里，同一 token 可以被多次提交但只有第一次能拿到有效 `passToken`，
   因为 `attempts` 计数会累积 —— 已足够，但显式 nonce 表更直观）。
4. **把限流换成 Redis** 以支持多实例精确计数。
5. **加行为采集**：鼠标轨迹、点击压力、设备指纹。这些信号与验证码结合，
   能显著提高识别脚本的准确率。
