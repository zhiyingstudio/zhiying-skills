## 1. 决定接在哪里

点选验证码适合放在**低频、高价值、易被脚本滥用**的入口：

| 场景 | 建议 | 理由 |
|---|---|---|
| 注册 | ✅ 强烈建议 | 挡批量注册；用户此时已有耐心 |
| 发送短信验证码 | ✅ 强烈建议 | 直接对应真金白银的短信费 |
| 领取优惠券 / 红包 | ✅ 强烈建议 | 防薅羊毛 |
| 密码重置 | ✅ 建议 | 防撞库 |
| 登录 | ⚠️ 谨慎 | 高频操作，会显著伤害体验。建议「失败 3 次后再出验证码」 |
| 每次提交表单 | ❌ 不要 | 过度使用会让用户反感并流失 |

> **经验值**：注册 + 发短信两个点加上就够了，覆盖率 90% 的滥用场景。

## 2. 后端改造的三个必改点

从示例代码到生产环境，只有三件事要做。

### ① secret 必须来自环境变量

```diff
- const captcha = createCaptcha({ secret: process.env.CAPTCHA_SECRET || crypto.randomBytes(32).toString("hex") });
+ const captcha = createCaptcha({ secret: process.env.CAPTCHA_SECRET });
```

**为什么**：示例里的 `|| crypto.randomBytes(...)` 是为了让你不改配置就能跑。
生产环境用它的后果是 —— **每次冷启动 secret 都变**，所有在途挑战立即失效，
用户会遇到「刚点完就提示验证过期」。必须在启动时硬失败：

```js
if (!process.env.CAPTCHA_SECRET) {
  throw new Error("缺少 CAPTCHA_SECRET，进程不应启动");
}
```

生成一个：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### ② 必须做服务端单例

```js
// ❌ 错误：每个 route 各建一个
export async function POST(req) {
  const captcha = createCaptcha({ secret: process.env.CAPTCHA_SECRET });  // 每次请求都新建！
  ...
}
```

问题在于 `passTokens` 存在**实例内存**里。签发挑战的实例和校验的实例不是同一个，
用户点对了也查不到凭证。

```js
// ✅ 正确：模块单例
// lib/captcha.js
import { createCaptcha } from "ink-captcha";
export const captcha = createCaptcha({ secret: process.env.CAPTCHA_SECRET });
```

Next.js 开发模式会热重载模块，再加一层 `globalThis` 缓存（见
[`examples/nextjs/lib/captcha.ts`](../examples/nextjs/lib/captcha.ts)）：

```js
const g = globalThis;
export const captcha = (g.__inkCaptcha ??= createCaptcha({ secret: ... }));
```

### ③ 业务接口必须消费凭证

```diff
  app.post("/api/register", (req, res) => {
    const { account, passToken } = req.body;

+   if (!captcha.consumePassToken(passToken)) {
+     return res.status(400).json({ success: false, error: "人机验证未通过或已失效" });
+   }
+
    // ... 注册逻辑
  });
```

**这是最常见的漏点**。现象是「验证码明明能过，但脚本还是能绕过」——
因为业务接口压根没检查过凭证。

> 💡 快速自查：全局搜 `consumePassToken`，确认它出现在**每一个**你希望被保护的接口里。

## 3. 前端 API 路径改成本地的

组件默认请求 `/api/captcha/points` 和 `/api/captcha/points/verify`。
如果你的路径不同，用配置覆盖：

```js
InkCaptcha.mount(el, {
  endpoint: "/v1/human-check",              // 改成你的
  verifyEndpoint: "/v1/human-check/verify",
});
```

响应结构不同也能适配 —— 通过 `responseKeys` 告诉组件怎么取值：

```js
InkCaptcha.mount(el, {
  responseKeys: {
    // 你的接口返回 { code: 0, result: {...} }
    challengeData: (json) => (json.code === 0 ? json.result : null),
    passToken: (json) => (json.code === 0 ? json.result.ticket : null),
    errorText: (json) => json.message || null,
  },
});
```

## 4. 换掉题库（可选但推荐）

默认题库是 40 个国风意象单字。如果你的站点调性不同，换掉它。

```js
const captcha = createCaptcha({
  secret: process.env.CAPTCHA_SECRET,
  charPool: ["购", "物", "车", "订", "单", "支", "付", "价", "格", "折", /* ... */],
});
```

**选字三原则**：

1. **字形差异大** —— 这是最重要的。以下这些组合容易认错，务必避开：
   - 日 / 曰　未 / 末　己 / 已 / 巳　l / 1 / I　O / 0
   - 干 / 千　天 / 夭　拔 / 拨　戌 / 戍 / 戊
2. **常用字** —— 生僻字会让用户盯着看半天，体验极差，且不增加任何安全性
3. **长度足够** —— 至少 `targetCount + distractorCount`（默认 8 个），
   建议留 3 倍冗余（24 个以上），否则同一用户短时间内可能反复见到同样的字

也可以用**数字**或**英文字母**（如果目标用户是国际用户）：

```js
charPool: ["2","3","4","5","6","7","8","9", /* 避开 0/1 和 o/l/I */],
```

## 5. 处理「验证通过后表单被提交但业务失败」

典型场景：用户通过了验证码 → 点提交 → 后端说「用户名已存在」→ 用户改个名字重提
→ **但凭证已经被消费掉了**，第二次提交会报「人机验证未通过」。

### 方案 A：失败后自动重置（最简单）

```js
const res = await fetch("/api/register", { ... });
const json = await res.json();
if (!json.success) {
  showError(json.error);
  inst.reset();          // ⬅ 重置验证码，用户重新点一次
  token = null;
}
```

用户体验：要重新点一遍验证码。**如果你觉得可接受，就用这个。**

### 方案 B：先做轻量校验，再消费凭证（推荐）

把「用户名是否重复」这类**无副作用**的检查前置到验证之前：

```js
// 步骤 1：轻量校验（不消费凭证）
app.post("/api/register/check", (req, res) => {
  const { account } = req.body;
  if (isAccountTaken(account)) {
    return res.json({ success: false, error: "该账号已被注册" });
  }
  res.json({ success: true });
});

// 步骤 2：真正提交时才消费凭证
app.post("/api/register", (req, res) => {
  const { account, passToken } = req.body;
  if (isAccountTaken(account)) return res.status(400).json({ ... });   // 再查一次（防竞态）
  if (!captcha.consumePassToken(passToken)) return res.status(400).json({ ... });
  // ... 写库
});
```

用户体验：不用重新点验证码。代价是要多写一个接口。

### 方案 C：允许凭证在短窗口内复用（不推荐）

`passMaxAgeMs` 调大 + 改成计数消费。**除非你非常清楚在做什么，否则别用** ——
这等于给重放攻击开了口子。

## 6. 多实例 / 集群部署

### 必须做：所有实例共享同一个 secret

否则用户在 A 实例拿到的挑战，请求被负载均衡到 B 实例时会直接 `invalid_token`。
现象是「**间歇性验证失败**」，很难排查。

```yaml
# k8s 示例
env:
  - name: CAPTCHA_SECRET
    valueFrom:
      secretKeyRef:
        name: captcha-secret
        key: secret
```

### 限流：加一层 nginx

内存限流器按进程计数，3 个实例 = 实际放行量 ×3。最简单且最可靠的补法是前置 nginx：

```nginx
# http 块
limit_req_zone $binary_remote_addr zone=captcha_issue:10m rate=1r/s;
limit_req_zone $binary_remote_addr zone=captcha_verify:10m rate=0.5r/s;

# server 块
location = /api/captcha/points {
    limit_req zone=captcha_issue burst=5 nodelay;
    proxy_pass http://backend;
}
location = /api/captcha/points/verify {
    limit_req zone=captcha_verify burst=10 nodelay;
    proxy_pass http://backend;
}
```

### 凭证跨实例共享（可选）

如果业务要求严格的一次性（比如防羊毛党跨实例重放），把 `passTokens` 换成 Redis。
在 `src/core.js` 里改三处即可，接口签名不变：

```js
// 原
passTokens.set(passToken, Date.now());
const ts = passTokens.get(passToken);
passTokens.delete(passToken);

// 换成 Redis（redis.v4 语法示意）
await redis.set(`inkcap:pt:${passToken}`, Date.now(), { PX: passMaxAgeMs });
const ts = await redis.get(`inkcap:pt:${passToken}`);
await redis.del(`inkcap:pt:${passToken}`);
```

注意：换成异步后，`verify` / `consumePassToken` 也要改成 `async`。

## 7. 上线检查清单

- [ ] `CAPTCHA_SECRET` 来自环境变量，且启动时校验非空
- [ ] secret 已加入密钥管理（**不要**提交进 git）
- [ ] `createCaptcha()` 是模块单例，不是每请求新建
- [ ] 每一个受保护接口都调用了 `consumePassToken()`
- [ ] 全站 HTTPS
- [ ] 发了 `Cache-Control: no-store`（挑战接口）
- [ ] 限流已生效（本机 curl 连打 30 次看是否 429）
- [ ] 前端验证失败后能自动重置（手动点错试一次）
- [ ] 多实例时所有实例 secret 一致（`kubectl exec` 进去 echo 一下比对）
- [ ] 移动端实测（iOS Safari / 微信内置浏览器 / 安卓 Chrome）
- [ ] 窄屏（320px）实测无溢出
- [ ] 极端失败兜底：验证码接口挂了，业务是否还能走（决定是否要降级放行）

### 关于最后一条的决策

**验证码接口挂了要不要放行？** 这是产品决策，没有标准答案：

- **放行**：可用性优先。注册流程不会因为验证码服务故障而中断，但会短暂裸奔
- **拦截**：安全优先。宁可暂停注册，也不让批量脚本趁虚而入

推荐折中：**接口连续失败 N 次后自动降级放行 + 打日志告警**。这样不会把用户挡死，
你也能第一时间知道出事了。
