# 常见问题

## 安装与依赖

**Q：真的零依赖吗？**

核心（`src/core.js`、`src/ink-background.js`、`src/rate-limit.js`）确实零依赖，
只 `import crypto from "node:crypto"`。前端组件（`src/ink-captcha.js`）也是纯浏览器
API，不依赖任何库。`examples/` 里的 express / next / react 是**示例自身的依赖**。

验证一下：

```bash
grep -rE "^import" src/
# src/core.js:import crypto from "node:crypto";
# src/index.js:（只有 re-export）
# 其他文件没有 import
```

**Q：需要 React 吗？**

不需要。`src/ink-captcha.js` 是纯原生 JS（UMD 格式，可直接 `<script src>` 引入）。
`src/react.jsx` 只是给 React 项目的一层薄封装，只是为了少写几行代码。

**Q：需要 Tailwind 吗？**

不需要，而且**特意避开了**。所有样式内联在 Shadow DOM 里，
不读取任何外部 CSS 类名。这样：

- 不会污染你的全局样式
- 不会被你的 CSS reset 搞坏
- 你换主题/换 UI 框架都不影响它

**Q：Node 版本要求？**

Node 18+。用到了 `crypto.randomInt`（Node 14.10+）、
`base64url` 编码（Node 15+）、`node:` 前缀导入（Node 16+）。
Node 18 是 LTS 底线，稳妥。

## 集成常见问题

**Q：用户点对了，但提交时提示「验证未通过或已失效」**

按这个顺序排查：

1. **业务接口有没有调 `consumePassToken()`？** —— 最高频原因，占一半以上
2. **`createCaptcha()` 是不是模块单例？** —— 如果每个 route 各建一个，
   签发实例和校验实例内存不互通（详见[接入指南第 2 节](./接入指南.md#2-后端改造的三个必改点)）
3. **多实例部署时 secret 是否一致？** —— 不一致会导致间歇性失败
4. **是不是同一凭证提交了两次？** —— 设计上第二次必然失败（防重放）

**Q：提示「验证已过期」**

- `challengeMaxAgeMs` 默认 5 分钟。用户如果开着页面去泡了杯茶再回来，
  就会过期 → 组件会自动拉新的，正常
- 如果**频繁**出现过期：多半是 secret 每次重启都变（示例里的
  `|| crypto.randomBytes(...)` 没删）

**Q：提示「操作过快，请重新点选」**

触发了时序判据（全部点击间隔 < 60ms）。可能原因：

- 真的是脚本
- 自动化测试脚本点太快 → 测试里在点击之间加 `await page.waitForTimeout(300)`
- 用户用了「连点器」类工具

如果觉得误伤，调低 `minHumanStepMs`（比如 30）。

**Q：验证码区域和页面其他元素重叠 / 高度不对**

组件挂载后卡片会 `transform: scale()` 缩放来适配窄屏。缩放后的元素**不占原始高度**，
所以组件会手动把外层 `.wrap` 的高度设成 `卡片高度 × scale`。

如果你把它放进 `display: flex` 且父容器高度固定，可能出现问题。
解法：给挂载容器一个明确的高度上下文，或直接让它作为块级元素独占一行。

**Q：多个验证码组件在同一页面上**

可以。每个实例是独立的 Shadow DOM，且底图 SVG 的渐变 id 用 seed 做了前缀，
不会互相覆盖渐变定义。

**Q：能自定义颜色/文案吗？**

- 文案：通过 `texts` 配置项，全部可覆盖
- 底图配色：`buildInkBackground({ theme: "paper" | "dark" })`
- 更细的配色：直接改 `src/ink-background.js` 里的 `paperTop` / `farInk` 等常量。
  没有做成配置项是因为选项太多反而不好调 —— 改源码更快

## 安全相关

**Q：答案在响应体里，脚本直接读不就行了？**

底图上的字必须让用户看见才能作答 —— 这是可用性的硬约束。
脚本能读到字和坐标，但**读不到「该按什么顺序点」**（那在加密 token 里）。

真正拦住脚本的是：必须走完整流程 + 一次性凭证 + 尝试次数上限 + IP 限流 + 时序判据。
详细论证见[安全说明第 3 节](./安全说明.md#3-为什么答案在响应体里不算漏洞)。

**Q：能挡住打码平台吗？**

不能，也不打算。所有图形验证码都挡不住。目标是把攻击成本抬到高于你的业务价值。

**Q：为什么不做成滑块？**

仓库同时也提供滑块版实现吗？没有 —— 我们是**用点选替代了滑块**。理由：

- 滑块容易被脚本用「轨迹模拟」绕过（且轨迹模拟的库已经烂大街）
- 点选式要求识别「多个字 + 顺序」，OCR/多模态成本明显更高
- 点选式天然是离散的（点哪个字），不依赖拖拽的像素级精度，移动端体验更好

**Q：`SECRET` 怎么管理？**

当数据库密码对待：

- 环境变量注入，不入库不入 git
- 用密钥管理服务（K8s Secret / Vault / 云厂商 KMS）
- 定期轮换 —— 注意轮换会让**所有在途挑战立即失效**，建议低峰期做

**Q：多实例部署要注意什么？**

两点：
1. 所有实例 secret 必须一致（否则间歇性 `invalid_token`）
2. 限流按进程计数，实际放行量 = 单实例限制 × 实例数 → 前面加 nginx `limit_req`

详见[接入指南第 6 节](./接入指南.md#6-多实例--集群部署)。

## 体验相关

**Q：为什么验证码那么大（320×200）？**

因为要塞 8 个中文字且保证可读。宽度再小，字就要缩小 → 长尾用户（
尤其是中老年用户）会看不清。320 宽在 375px 的手机屏上刚好放下，
更窄的屏会等比缩放。

如果你要缩小，**同时改 `width` / `height` / `minCenterGap`** ——
只改画布不改间距会导致字挤在一起。

**Q：用户老点错，是不是太难了？**

可能原因与解法：

| 原因 | 解法 |
|---|---|
| 题库里有易混字 | 检查你的 `charPool`，剔掉「日/曰」「未/末」这类 |
| 字号太小 | 提高基础字号（`core.js` 里 `size: 26 + randomInt(0,7)`） |
| 底图对比度太低 | 改 `buildInkBackground` 里山的透明度，或让字的描边更粗 |
| 目标字数太多 | `targetCount` 从 4 降到 3 |

**Q：能不能在验证通过后自动提交表单？**

不建议。用户预期是「我点了提交才提交」。自动提交会让人困惑
（尤其是还能改输入框的时候）。如果确实要，用 `onVerified` 回调里触发。

**Q：验证码加载慢怎么办？**

底图是服务端实时生成的 SVG（约 17KB），生成耗时 < 1ms。
如果感觉慢，通常是网络问题。可以考虑：

- 底图 SVG 加 `Cache-Control: no-store`（已默认，因为每次都不一样）
- 或者接受轻微延迟，不要为了「预加载」而在页面初始就请求（浪费配额）

## 开发相关

**Q：怎么跑测试？**

```bash
npm test                                    # 核心逻辑，36 项，零依赖
node scripts/preview-sheet.mjs              # 生成底图对照页（浏览器打开看）
node scripts/browser-e2e.mjs http://localhost:3737   # 真实浏览器端到端
```

**Q：怎么调试底图？**

用固定 seed 生成可复现的图：

```js
buildInkBackground({ width: 320, height: 200, seed: 12345 });
```

`scripts/preview-sheet.mjs` 就是个现成的例子 —— 一次并排看 12 张。

> 💡 **别只看一张就下结论**。底图效果受 seed 影响很大，
> 单看一张可能会误判「字都挤在一起」或「位置分布很好」。
> 这是我们踩过的坑：一开始只看一张觉得没问题，并排看 12 张才发现
> 「目标字有时全挤在同一侧」。

**Q：怎么改布点算法？**

在 `src/core.js` 的 `layout()` 和 `createChallenge()` 里。关键约束：

1. 字不能重叠（`minCenterGap`，失败会逐步放宽到 38 再走网格兜底）
2. 字不能压边（`marginX: 42` / `marginTop: 32` / `marginBottom: 38`）
3. 字不能压右下角印章（`inSealZone()`）
4. 目标字之间要分散（爬山法优化）

改完**务必跑 `npm test`** —— 里面有针对这四条的定量断言。

**Q：为什么字有旋转？**

两个原因：视觉上更自然（像散落的字），以及提高 OCR 难度。
范围是 ±18 度 —— 再大就影响可读性了。

## 其他

**Q：能商用吗？**

MIT 协议，可以。保留 LICENSE 文件即可。

**Q：为什么叫 ink-captcha？**

底图是水墨风格（ink wash），点是点选。名字直白好记。

**Q：会不会有合规问题？**

本组件不收集、不上传任何用户数据，所有校验在你自己的服务器内存中完成，
不使用任何第三方打码/验证服务。这本身规避了「用户数据出境」
和「依赖境外验证服务」这两类常见问题。

但如果你的业务属于《互联网用户账号信息管理规定》等法规监管的范畴，
请自行评估是否需要叠加其他合规措施。我们提供的是技术组件，不构成合规建议。
